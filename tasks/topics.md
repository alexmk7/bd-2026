## Краткое введение в устройство операционных систем и управление памятью

#### Процессор

1. Процессор может выполнять специальные инструкции, которые зависят от архитектуры — машинный код.
2. Очень упрощённо: процессор может оперировать регистрами (внутрипроцессорные сверхбыстрые ячейки памяти) и основной памятью. Помимо этого между процессором и основной памятью существует несколько уровней кэша (`L1`, `L2`, `L3`) — чем ближе к ядру, тем быстрее, но тем меньше объём. Промах кэша (`cache miss`) дорого обходится по времени.
3. Современные процессоры в основном многоядерные. Каждое ядро может независимо выполнять поток инструкций. Технология `Hyper-Threading` (Intel) / `SMT` позволяет одному физическому ядру представляться как два логических.
4. Инструкции процессора оперируют основной памятью и регистрами. Писать и читать в регистры намного быстрее. Современные процессоры активно используют конвейеризацию, суперскалярное выполнение и выполнение вне порядка (`out-of-order execution`) для повышения `IPC` (instructions per cycle).
5. Режимы работы процессора: `user mode` (непривилегированный, для пользовательских программ) и `kernel mode` (привилегированный, для ядра ОС). Переключение между ними происходит при системных вызовах (`syscall`) и прерываниях.

Следующая программа на языке `C`:
```c
#include<stdio.h>

int main(int argc, char *argv[]) {
    int a = 2;
    int b;

    b = (a + 17) * 9;

    printf("%d\n", b);

    return 0;
}
```

может транслироваться в программу на ассемблере (упрощённо: удобочитаемая форма машинного кода):

```asm
# int main(int argc, char *argv[]) {
   push   %rbp
   mov    %rsp,%rbp
   sub    $0x20,%rsp
   mov    %edi,-0x14(%rbp)
   mov    %rsi,-0x20(%rbp)

# int a = 2;
   movl   $0x2,-0x8(%rbp)

# int b;
# b = (a + 17) * 9;
   mov    -0x8(%rbp),%eax
   lea    0x11(%rax),%edx
   mov    %edx,%eax
   shl    $0x3,%eax
   add    %edx,%eax
   mov    %eax,-0x4(%rbp)

# printf("%d\n", b);
   mov    -0x4(%rbp),%eax
   mov    %eax,%esi
   lea    0x98(%rip),%rdi        # 0x714
   mov    $0x0,%eax
   callq  0x520 <printf@plt>
```

`%eax`, `%..` — это регистры. `mov` — скопировать данные из источника в приёмник (регистр, ячейка основной памяти). `lea` вычисляет адрес без обращения к памяти и часто используется для арифметики. Компилятор заменил умножение на 9 более дешёвой комбинацией сдвига и сложения (`shl + add`).

Исполняемые файлы (`PE` (.exe) для ОС семейства Windows, `ELF` для \*nix) и динамические библиотеки (`.dll` и `.so`) содержат в том числе машинный код в бинарном виде, который может прямо выполняться процессором.

#### Управление памятью

1. Очень упрощённо — каждый процесс имеет своё **виртуальное адресное пространство**. Это пространство разделено на регионы — страницы фиксированного размера (типично 4 КБ; большие страницы — `huge pages` — 2 МБ или 1 ГБ).
2. Каждая страница отображается (или не отображается) в страницу физической памяти с помощью аппаратного блока `MMU` (Memory Management Unit) и таблиц страниц (`page tables`). Трансляция адресов кэшируется в `TLB` (Translation Lookaside Buffer).
3. Страницы двух разных процессов могут отображаться в одну и ту же страницу физической памяти — это используется для разделяемых библиотек и межпроцессного взаимодействия через `shared memory`.
4. Когда не хватает физической памяти, неиспользуемые страницы могут сбрасываться на диск (`swap`/`page file`). Это называется **свопинг** или **пейджинг**. Обращение к такой странице вызывает `page fault` — прерывание, при котором ОС подгружает нужную страницу обратно в RAM.
5. В \*nix системах есть системный вызов `fork`, который позволяет быстро создать копию процесса с помощью механизма **copy-on-write** (`CoW`): страницы памяти физически не копируются сразу — копия создаётся только при попытке записи в страницу.
6. Сегменты виртуального адресного пространства процесса: `text` (код программы, read-only), `data` (глобальные и статические переменные), `heap` (динамическая память, растёт вверх), `stack` (стек вызовов, растёт вниз), а также отображения разделяемых библиотек (`mmap`).

#### Процессы и потоки

1. **Процесс** — основная единица выполнения операционной системы (очень условно). Работает в своём виртуальном адресном пространстве. Имеет как минимум один поток. Изолирован от других процессов — напрямую обратиться к памяти другого процесса нельзя.
2. **Поток** — линейный процесс выполнения набора инструкций. В рамках процесса в одном и том же адресном пространстве могут выполняться несколько потоков. Основная цель — параллельное выполнение каких-то действий (на многоядерных процессорах оно действительно может работать параллельно). Потоки одного процесса разделяют кучу (`heap`), глобальные переменные и дескрипторы файлов, но имеют независимые стеки и регистры.
3. Планировщик ОС (`scheduler`) решает, какой поток/процесс запускать в следующий квант времени. В Linux может использоваться планировщик `CFS` (Completely Fair Scheduler). Переключение контекста (`context switch`) — дорогостоящая операция.
4. Межпроцессное взаимодействие (`IPC`): `pipes`, `named pipes` (`FIFO`), сокеты, разделяемая память (`shm`), очереди сообщений, сигналы.


## Docker

1. Docker позволяет обеспечить изоляцию и удобное развёртывание приложений в Linux-системах, ограничив доступ к файлам, памяти, процессору, подменив сетевые интерфейсы, `userland` и так далее.
2. Используются специфичные механизмы ядра Linux — `cgroups` (control groups, для ограничения и учёта потребления ресурсов: CPU, RAM, I/O) и `namespaces` (для изоляции: PID, network, mount, IPC, UTS, user namespace).
3. Docker можно установить под любую распространённую операционную систему, но для Windows или macOS требуется использование системы виртуализации, в которой запускается ядро Linux, что может сказаться на производительности и использовании ресурсов.
4. С помощью Docker удобно автоматизировать процесс развёртывания приложений и запуска в изолированном окружении.
5. **Образ** (`image`) — это неизменяемый образ файловой системы и набор вспомогательной мета-информации. Образы могут состоять из слоёв — срезов файловой системы, которые накладываются друг на друга. Например, образы двух разных версий Python могут иметь один общий слой — базовый набор библиотек операционной системы (см. `OverlayFS`). Каждый слой соответствует инструкции в `Dockerfile` и кэшируется.
6. Готовый образ можно импортировать на локальную машину из удалённого реестра (Docker Hub, GHCR, ECR и др.) командой `docker pull`.
7. Образ можно собрать локально с помощью инструкций в `Dockerfile` командой `docker build`.
8. **Контейнер** — процесс, который запускается в изолированном окружении на основе образа. При запуске создаётся writable-слой, который накладывается на образ (copy-on-write). Контейнер можно запустить, остановить, перезапустить, удалить (в этом случае все данные writable-слоя будут потеряны), создать на основе работающего контейнера новый образ.
9. `Volumes` — механизм для сохранения данных вне контейнера (монтируются в файловую систему контейнера). Позволяют данным переживать пересоздание контейнера.
10. `Docker Compose` — инструмент для декларативного описания и запуска многоконтейнерных приложений через `docker-compose.yml`. `Docker Swarm` и `Kubernetes` решают задачи оркестрации на уровне кластера.
11. Сети в Docker: по умолчанию контейнеры получают изолированную сеть (`bridge`). Можно пробрасывать порты (`-p 8080:80`), использовать `host`-сеть или `overlay`-сети для связи между узлами кластера.

## Python: потоки, процессы, примитивы синхронизации

#### CPython

Python — скриптовый язык программирования со строгой динамической типизацией.

Основная реализация: `CPython`. Другие: `PyPy` (JIT-компилятор), `GraalPython`, `Jython` (JVM), различные модификации CPython.

Интерпретатор CPython конвертирует исходный код в специальный **байт-код** стековой машины (можно посмотреть через модуль `dis`).

1. Ядро интерпретатора CPython — большой цикл (`ceval.c`), в котором последовательно обрабатываются инструкции байт-кода.
2. В CPython реализована автоматическая модель управления памятью, нет необходимости вручную удалять объекты. Основа — **счётчик ссылок** (reference counting) с дополнительным сборщиком мусора для обнаружения циклических ссылок (модуль `gc`). Счётчик ссылок — синхронный и детерминированный, поэтому большинство объектов уничтожается немедленно при выходе из области видимости.
3. CPython в общем случае весьма неэффективный интерпретатор — как по эффективности использования памяти (каждый объект несёт накладные расходы), так и по скорости выполнения программ. Начиная с CPython 3.11 ведётся активная работа по ускорению интерпретатора (проект «Faster CPython»).
4. По состоянию на 3.14 в CPython по умолчанию существует **GIL** (Global Interpreter Lock — глобальная блокировка интерпретатора). Только один пользовательский поток может выполнять байт-код Python в конкретный момент времени. Это обеспечивает потокобезопасность внутренних структур интерпретатора, но ограничивает параллелизм для CPU-bound задач. Начиная с 3.13 экспериментально доступен режим no-GIL (free-threaded CPython, PEP 703).
5. Некоторые библиотеки (`NumPy`, `pandas`, библиотеки ввода-вывода и др.) при выполнении определённых операций отпускают GIL, позволяя другим потокам работать параллельно.

#### Потоки

1. Для запуска потока нужно создать экземпляр класса `Thread` из модуля `threading`, передав функцию и её аргументы. Метод `start()` запускает поток, `join()` — ожидает его завершения.
2. Создание потоков — тяжёлая операция. Можно переиспользовать потоки с помощью `ThreadPoolExecutor` (модуль `concurrent.futures`) или `ThreadPool` (модуль `multiprocessing.pool`). Метод `submit()` возвращает объект `Future`.
3. При обращении к общим ресурсам из разных потоков нужно использовать механизмы синхронизации:
   - `Lock` — базовый мьютекс (взаимное исключение).
   - `RLock` — реентерабельный мьютекс (один поток может захватить его несколько раз).
   - `Semaphore` — счётный семафор, ограничивает количество одновременно работающих потоков.
   - `Event` — флаг для сигнализации между потоками.
   - `Condition` — позволяет потокам ждать выполнения условия (`wait`/`notify`).
   - `Queue` — потокобезопасная очередь для передачи данных между потоками (FIFO, LIFO, PriorityQueue).
4. Потоки хорошо подходят для **I/O-bound** задач (сетевые запросы, работа с файлами), где большую часть времени поток ожидает внешнего ответа и GIL освобождается.

#### Процессы

1. Так как в CPython есть GIL, использование потоков для **CPU-bound** задач чаще всего не даёт выигрыша в производительности.
2. Альтернатива — модуль `multiprocessing`. Создаются отдельные дочерние процессы со своими интерпретаторами Python, каждый со своим GIL. Они могут параллельно выполнять вычислительно интенсивные функции. Аналог `ThreadPoolExecutor` — `ProcessPoolExecutor`.
3. Под разные системы используются разные подходы к запуску дочерних процессов:
   - `fork` — копирует процесс (CoW), быстро, но небезопасно с некоторыми библиотеками (macOS, Linux).
   - `spawn` — запускает чистый интерпретатор Python и импортирует модуль (медленнее, но безопаснее; по умолчанию на Windows и macOS).
   - `forkserver` — запускает отдельный сервер, который выполняет `fork` по запросу.
4. Для синхронизации и доступа к общим данным используются: `Pipe` (двустороннее соединение), `Queue` (межпроцессная очередь), `Manager` (прокси-объекты для разделяемых структур данных), `Lock`, `Value` и `Array` (разделяемая память).
5. Для работы с большими данными можно использовать `memory-mapped files` (`mmap`) — позволяет нескольким процессам работать с одним файлом через общее адресное пространство.
6. `concurrent.futures` предоставляет единый интерфейс (`Executor`) для работы как с потоками (`ThreadPoolExecutor`), так и с процессами (`ProcessPoolExecutor`), что упрощает переключение между ними.


## HDFS

1. **Hadoop Distributed File System** — распределённая файловая система, развивающаяся в рамках проекта Apache Hadoop. С точки зрения пользователя представляет собой классическую иерархическую файловую систему (в отличие от, например, object storage), с файлами, директориями, правами доступа.
2. Файлы хранятся распределённо, реплицируются; система устойчива к отказам оборудования.
3. HDFS имеет свои ограничения, отличающие её от классических локальных ФС. Дизайн изначально был рассчитан на паттерн **WORM** (write once, read many) в рамках MapReduce: эффективна для больших последовательных чтений, плохо подходит для случайного доступа и множества мелких файлов.
4. Система горизонтально масштабируема; запускалась на кластерах ~4000 машин.
5. HDFS необязательно использовать вместе с MapReduce — систему можно использовать независимо.
6. Архитектура: `NameNode` — машина, на которой хранятся метаданные файловой системы (namespace, маппинг блоков на DataNode'ы); `DataNode` — машины, на которых хранятся непосредственно данные. Для отказоустойчивости NameNode используется `Secondary NameNode` или режим `HA` (High Availability) с двумя NameNode'ами (active/standby через ZooKeeper).
7. Файлы делятся на блоки (по умолчанию 128 МБ).
8. Каждый блок хранится на какой-то `DataNode`.
9. Каждый блок файла реплицируется по другим `DataNode` по сети (по умолчанию на 3 узла — `replication factor`). Политика размещения учитывает стойки (`rack awareness`) для устойчивости к отказу целой стойки.
10. `NameNode` отслеживает состояние каждого узла через `heartbeat`-сообщения.
11. Если узел стал недоступен, блок автоматически до-реплицируется.
12. `DataNode`'ы умеют общаться друг с другом (например, при конвейерной записи).
13. `HDFS Federation` позволяет использовать множество NameNode для горизонтального масштабирования пространства имён.
14. Есть система контроля доступа и авторизации (POSIX-подобные ACL, интеграция с Kerberos).

## YARN

1. **YARN** (Yet Another Resource Negotiator) — система управления ресурсами, составная часть Apache Hadoop, начиная с версии 2.0.
2. Мотивация: есть большой кластер и нужно запускать на нём задачи, выделяя каждой необходимые ресурсы (CPU, RAM), ограничивая и квотируя их, наблюдать за состоянием задач и оборудования.
3. `ResourceManager` — управляет ресурсами всего кластера. Кластер обычно имеет один основной ResourceManager (с резервным для HA). Состоит из `Scheduler` (распределяет ресурсы) и `ApplicationManager` (управляет жизненным циклом приложений).
4. `NodeManager` — агент на каждом рабочем узле, отвечающий за запуск контейнеров и отчётность о ресурсах перед ResourceManager. Запускается на тех же машинах, что и DataNode.
5. `ApplicationMaster` — компонент, запускаемый для каждого приложения (задачи). Он переговаривается с ResourceManager за ресурсы и управляет выполнением задачи на NodeManager'ах.
6. Контейнер в терминологии YARN — выделенный набор ресурсов (CPU + RAM) на конкретном узле.

## MapReduce

1. Модель вычислений и фреймворк для распределённой обработки данных. Пользователь пишет функции `map` (преобразует входную запись в набор пар ключ-значение) и `reduce` (агрегирует все значения для одного ключа). Между ними происходит фаза **shuffle & sort** — данные перераспределяются по ключу и сортируются. Опционально указываются `combiner` (локальная предагрегация на mapper'е) и функции партиционирования.
2. Важное свойство — **Data Locality**: планировщик старается запустить mapper на той же машине, где лежат данные, чтобы минимизировать сетевой трафик.
3. Hadoop MapReduce — приложение для YARN.
4. Популярен до середины 2010-х. Проблемы: долгий запуск (overhead JVM), промежуточные данные сбрасываются на диск, сложность с итерационными алгоритмами, громоздкость кода.
5. До сих пор используется в ряде устаревших enterprise-систем.

## Hive

1. Преобразует запрос на диалекте SQL — `HiveQL` — в последовательность задач (MapReduce, Tez или Spark). Данные хранятся в файлах на HDFS и интерпретируются как таблицы с помощью метаданных в `Hive Metastore`.
2. К таблицам Hive можно обращаться из других систем (Apache Spark, Trino/Presto и др.) через `Hive Metastore` как общий каталог схем.
3. Поддерживает разные форматы хранения: `TextFile`, `ORC`, `Parquet`, `Avro`. Колоночные форматы (`ORC`, `Parquet`) дают значительный выигрыш для аналитических запросов.
4. Поддерживает партиционирование таблиц и бакетирование для оптимизации запросов.

## ZooKeeper

1. Распределённый координационный сервис для распределённых приложений, предназначенный для управления конфигурациями, синхронизацией, обменом вспомогательными данными между узлами.
2. Очень упрощённо ZooKeeper можно рассматривать как аналог примитивов синхронизации для распределённых систем.
3. Данные организованы в иерархическую древовидную структуру — `znodes` (аналог файловой системы). Каждому узлу можно присвоить значение. Данные хранятся в памяти — отсюда высокая производительность и малые задержки.
4. Типы znodes: `persistent` (существуют до явного удаления), `ephemeral` (удаляются при потере сессии клиента — полезно для leader election и обнаружения отказов), `sequential` (к имени добавляется уникальный монотонный номер).
5. Механизм `watches` позволяет клиентам подписываться на изменения znode и получать уведомления — основа для реализации распределённых блокировок, барьеров, очередей.
6. Упор на высокой производительности, масштабируемости, надёжности и отказоустойчивости. Ансамбль ZooKeeper обычно состоит из нечётного числа узлов (3, 5); большинство (`quorum`) необходимо для подтверждения операций.
7. Гарантируется строгая последовательность операций записи и чтения (`linearizability` для записей, `sequential consistency` для чтений).
8. Используется в экосистеме Hadoop: управление HA для NameNode и ResourceManager, координация Kafka (до KRaft), HBase и др.

## Spark

1. Фреймворк для аналитических вычислений и распределённой обработки больших данных.
2. Устраняет недостатки Hadoop MapReduce: данные хранятся в памяти (in-memory), возможны онлайн и итерационные вычисления (ML), меньше операций с диском.
3. Изначально применялась концепция `RDD` (Resilient Distributed Dataset) — неизменяемая распределённая коллекция. Трансформации ленивые (lazy), вычисления материализуются при вызове `action`. Минусы: невозможность оптимизировать хранение и план выполнения, неэффективность кода не на JVM.
4. Новый подход: `SparkSQL`, `Dataset` и `DataFrame`. Данные хранятся off-heap в бинарном виде (Project Tungsten), могут храниться по столбцам. Оптимизатор `Catalyst` строит и оптимизирует логический и физический планы выполнения запроса. `AQE` (Adaptive Query Execution) динамически перепланирует выполнение на основе статистик runtime.
5. `Pandas API` (`pyspark.pandas`) и `SQL API` для знакомого интерфейса.
6. Библиотеки: `MLlib` (машинное обучение), `GraphX` / `GraphFrames` (работа с графами), `Spark Streaming` / `Structured Streaming` (потоковая обработка).
7. Режимы запуска: `local`, `standalone cluster`, `YARN`, `Kubernetes`, `Mesos`. Конфигурируется через `SparkConf` или `spark-submit`.
8. Ключевые параметры производительности: количество и размер партиций, число executor'ов и ядер, настройка shuffle (узкое место), кэширование (`cache()` / `persist()`).


## MinIO

1. `MinIO` — высокопроизводительное объектное хранилище с открытым исходным кодом, совместимое с `Amazon S3 API`. Написано на Go.
2. **Object Storage** — парадигма хранения данных, отличная от файловых систем (иерархия директорий) и блочных устройств. Данные хранятся как объекты в плоском пространстве имён внутри `bucket`'ов. Каждый объект = данные + метаданные + уникальный ключ. Хорошо масштабируется горизонтально, но не поддерживает частичное обновление объекта (только перезапись целиком) и имеет более высокую латентность по сравнению с файловыми системами.
3. Совместимость с S3 означает, что любой клиент, написанный под AWS S3 (`boto3`, AWS SDK, `spark-hadoop-aws` и др.), будет работать с MinIO без изменений — достаточно поменять endpoint.
4. MinIO может работать в нескольких режимах:
   - `single-node single-drive` — для разработки и тестирования.
   - `single-node multi-drive` — повышенная надёжность на одной машине через erasure coding.
   - `distributed` (multi-node multi-drive) — production-режим: данные распределяются по нескольким узлам.
5. **Erasure Coding** — механизм избыточности, используемый вместо простой репликации. Объект разбивается на `N` data-шардов и `K` parity-шардов (аналог RAID). Объект можно восстановить при потере до `K` шардов. Erasure Coding даёт лучшее соотношение надёжности к объёму хранимых данных по сравнению с 3x-репликацией.
6. `Bitrot protection` — MinIO вычисляет и сохраняет контрольную сумму каждого шарда. При чтении данные верифицируются; повреждённый шард восстанавливается из parity.
7. MinIO гарантирует **строгую согласованность** (strong consistency) для операций `GET`/`PUT`/`DELETE` на уровне объекта, в отличие от eventual consistency в оригинальном S3.
8. `Versioning` — поддержка версионирования объектов (аналогично S3). При включённом версионировании `PUT` не перезаписывает объект, а создаёт новую версию. Полезно для защиты от случайного удаления.
9. `Lifecycle policies` — автоматическое управление объектами: переход в более дешёвый storage tier или удаление по истечении срока.
10. MinIO активно используется в Data-платформах как замена S3 в on-premise кластерах: в связке с Spark, Trino, Hive Metastore, Delta Lake, Apache Iceberg.
11. Через коннектор `s3a://` Spark и другие инструменты экосистемы Hadoop могут работать с MinIO так же, как с HDFS.

## Ceph

1. `Ceph` — унифицированная распределённая система хранения с открытым исходным кодом, предоставляющая одновременно три интерфейса: объектное хранилище (совместимое с S3), блочные устройства (`RBD` — Rados Block Device) и файловую систему (`CephFS`). Написана преимущественно на C++.
2. Ключевое отличие от большинства аналогов — **отсутствие центрального метаданного сервера** для объектного и блочного хранилища. Вместо этого используется алгоритм `CRUSH` (Controlled Replication Under Scalable Hashing) для детерминированного вычисления расположения данных: клиент сам вычисляет, на каком OSD лежит нужный объект, без обращения к посреднику.
3. Архитектурные компоненты:
   - `OSD` (Object Storage Daemon) — процесс, управляющий одним физическим диском. Отвечает за хранение данных, репликацию, восстановление и heartbeat с другими OSD. Типично один OSD на диск.
   - `MON` (Monitor) — поддерживает карту кластера (`cluster map`: CRUSH map, OSD map, PG map). Обеспечивает кворум (обычно 3 или 5 узлов). Клиенты обращаются к MON для получения актуальной карты.
   - `MGR` (Manager) — собирает метрики, предоставляет REST API и дашборд. Обычно работает в паре active/standby.
   - `MDS` (Metadata Server) — нужен только для CephFS. Управляет метаданными файловой системы (директории, inode'ы). Поддерживает несколько активных MDS для горизонтального масштабирования.
4. `RADOS` (Reliable Autonomic Distributed Object Store) — базовый слой хранения Ceph. Все вышестоящие интерфейсы (`RBD`, `CephFS`, `RGW`) построены поверх него.
5. `Placement Groups` (`PG`) — промежуточный уровень абстракции между объектами и OSD. Объекты хешируются в PG, PG маппируются на OSD через CRUSH. Это позволяет эффективно перебалансировать данные при добавлении/удалении узлов: перемещаются не отдельные объекты, а целые PG.
6. `CRUSH map` — описывает топологию кластера (хосты, стойки, датацентры) и политики размещения данных. Позволяет гарантировать, что реплики одного объекта попадут на разные стойки или датацентры (`rack`/`datacenter awareness`) — аналог HDFS rack awareness, но более гибко.
7. Ceph поддерживает два механизма избыточности на уровне пулов (`pool`): replicated pool — проще, ниже латентность; EC pool (Erasure Coding) — выгоднее по объёму, но выше накладные расходы при записи (нужно вычислить parity), не поддерживается для RBD и CephFS напрямую.
8. Самовосстановление: при выходе OSD из строя Ceph автоматически переводит затронутые PG в состояние деградации и начинает восстановление из оставшихся реплик. Процесс называется `backfill`/`recovery` и управляется с ограничением по пропускной способности, чтобы не мешать клиентским операциям.
9. `CephFS` — POSIX-совместимая распределённая файловая система поверх RADOS. Поддерживает несколько клиентов с одновременным доступом (в отличие от большинства сетевых блочных устройств). Используется как замена NFS в HPC и как persistent volume в Kubernetes.

## Ray

1. Фреймворк для распределённых вычислений и масштабирования Python-приложений (в т.ч. ML).
2. `Tasks` — удалённые функции, запускаемые асинхронно как отдельные задачи. Вызываются через декоратор `@ray.remote` и `f.remote(...)`, возвращают `ObjectRef`.
3. `Actors` — stateful-процессы: класс, помеченный `@ray.remote`, инстанцируется в кластере и сохраняет состояние между вызовами методов. Полезны для серверов, кэшей, шедулеров.
4. `Objects` — неизменяемые объекты в распределённом Object Store (разделяемая память внутри узла, сеть между узлами). Доступны через `ObjectRef`; `ray.get()` — синхронно получить значение, `ray.put()` — поместить объект.
5. Экосистема: `Ray Tune` (гиперпараметрический поиск), `Ray Train` (распределённое обучение), `Ray Serve` (деплой ML-моделей), `RLlib` (reinforcement learning).

## Parquet

1. `Apache Parquet` — колоночный формат хранения данных с открытым исходным кодом, разработанный для экосистемы Hadoop. Не зависит от конкретного фреймворка обработки данных — поддерживается Spark, Hive, Trino, Pandas, DuckDB и многими другими.

2. **Колоночное хранение**: данные одного столбца записываются на диск последовательно, а не построчно. Для аналитических запросов, обращающихся к небольшому числу столбцов из широкой таблицы, это даёт два ключевых преимущества: читаются только нужные столбцы (column pruning), а данные одного типа хорошо сжимаются.

3. **Структура файла**: файл делится на `row group`'ы — горизонтальные срезы таблицы (по умолчанию ~128 МБ). Внутри каждого `row group` данные каждого столбца хранятся в отдельном `column chunk`, который в свою очередь разбит на `page`'ы (~1 МБ) — минимальная единица сжатия и кодирования. В конце файла находится `footer` с метаданными: схема, статистики (min/max/null count) по каждому `row group` и `column chunk`, смещения для навигации по файлу.

4. **Predicate pushdown**: благодаря статистикам в `footer` читатель может пропустить целые `row group`'ы, не удовлетворяющие условию фильтрации (`WHERE col > X`), без чтения самих данных. Это называется `row group filtering` или `predicate pushdown`.

5. **Кодирование** (`encoding`): помимо обычного сжатия, Parquet применяет специализированные схемы кодирования, адаптированные к типу данных:
   - `RLE` (Run-Length Encoding) — эффективно для столбцов с повторяющимися значениями.
   - `Dictionary encoding` — значения заменяются индексами в словаре; эффективно для столбцов с низкой кардинальностью (например, статусы, категории).
   - `Delta encoding` — хранит разности между последовательными значениями; эффективно для монотонно возрастающих данных (timestamp'ы, id).
   - `Bit packing` — упаковка целых чисел в минимальное количество бит.

6. **Сжатие** (`compression`): применяется поверх кодирования на уровне `page`. Поддерживаются `Snappy` (быстро, умеренное сжатие, de-facto стандарт), `Gzip` (лучше сжимает, медленнее), `Zstandard` (`zstd`, хороший баланс), `LZ4`, `Brotli`. Выбор кодека влияет на соотношение скорость/размер.

7. **Схема и вложенные типы**: поддерживаются вложенные структуры (`struct`), списки (`list`) и словари (`map`) через механизм `repetition level` и `definition level` — позволяют эффективно хранить nullable-поля и вложенные коллекции.

8. **Эволюция схемы** (`schema evolution`): Parquet поддерживает добавление новых столбцов и удаление старых между версиями файлов. При чтении нескольких файлов с разными схемами фреймворк (Spark, Hive и др.) объединяет схемы (`schema merging`). Переименование и изменение типов столбцов не поддерживается без перезаписи.

9. **Партиционирование**: довольно часто  Parquet-файлы хранят в партиционированных директориях по значению одного или нескольких столбцов (например, `dt=2024-01-01/region=EU/file.parquet`). Это стандарт `Hive-style partitioning`. При запросе с фильтром по партиционному столбцу фреймворк пропускает целые директории (`partition pruning`) — в дополнение к `predicate pushdown` внутри файла.

10. Parquet — **неизменяемый** формат: данные записываются один раз, случайное обновление строк невозможно. Для поддержки `UPDATE`/`DELETE` поверх Parquet строятся табличные форматы: `Delta Lake`, `Apache Iceberg`, `Apache Hudi`. Они добавляют транзакционность, версионирование и управление файлами поверх обычных Parquet-файлов на хранилище.

11. Parquet хорошо интегрируется с `Apache Arrow` — колоночным форматом данных в памяти. `Arrow` и Parquet используют совместимые колоночные представления, что позволяет эффективно читать Parquet напрямую в Arrow-буферы без лишних копирований (`zero-copy`). Это используется в `pandas`, `DuckDB`, `Polars`.


## Общие вопросы

1. **Большие данные** — понятие относительно и контекстно-зависимо. Традиционно описывается концепцией **трёх V**: Volume (объём), Velocity (скорость генерации и обработки), Variety (разнообразие форматов). Иногда добавляют ещё Veracity (достоверность) и Value (ценность).

2. **Теорема CAP** (Brewer, 2000) утверждает, что распределённая система не может одновременно гарантировать все три свойства: **Consistency** (согласованность — все узлы видят одинаковые данные), **Availability** (доступность — каждый запрос получает ответ), **Partition tolerance** (устойчивость к разделению сети). При сетевом разделе приходится выбирать между C и A. На практике системы классифицируют как `CP` (напр., ZooKeeper, HBase) или `AP` (напр., Cassandra, DynamoDB). Теорема упрощает реальность; более точная модель — `PACELC`.

3. **OLTP** и **OLAP** — два принципиально разных паттерна работы с данными. OLTP (Online Transaction Processing) — много коротких транзакций, обращающихся к небольшому числу строк (интернет-магазины, банки). OLAP (Online Analytical Processing) — сложные аналитические запросы, сканирующие большие объёмы данных. Разные требования приводят к разным архитектурам БД и хранилищ.

4. Хранение данных по строкам (`row-oriented`) или столбцам (`column-oriented`). Row-oriented (PostgreSQL, MySQL) — все поля одной записи хранятся рядом, эффективно для OLTP. Column-oriented (Parquet, ORC, ClickHouse, Redshift) — все значения одного столбца хранятся рядом, эффективно для OLAP: высокая степень сжатия (одинаковые типы), vectorized execution, чтение только нужных столбцов. `PAX` (Partition Attributes Across) — гибридный подход.

5. **Raft** — алгоритм консенсуса в распределённых системах. Разработан как более понятная альтернатива Paxos. Элементы: `leader election` (выбор лидера, который принимает все записи), `log replication` (лидер реплицирует лог на follower'ов; запись считается зафиксированной после подтверждения большинством), `safety` (не более одного лидера в один момент). Используется в `etcd`, `CockroachDB`, `TiKV`.

6. Рандомизированные и вероятностные алгоритмы на больших данных: при работе с Big Data точные вычисления часто слишком дороги, поэтому используют приближённые структуры:
   - `HyperLogLog` — приближённый подсчёт числа уникальных элементов (cardinality estimation) с потреблением памяти O(log log N). Ошибка ~2%.
   - `Bloom Filter` — вероятностная структура для проверки принадлежности элемента к множеству. Возможны ложноположительные срабатывания (false positive), но не ложноотрицательные. Размер и процент ошибок настраиваются.
   - `Count-Min Sketch` — приближённый подсчёт частот элементов в потоке.
   - `MinHash` / `LSH` — приближённое вычисление сходства множеств (Jaccard similarity) без попарного сравнения.
