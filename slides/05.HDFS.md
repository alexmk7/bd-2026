## Что такое DFS?

**DFS (Distributed File System)** — распределённая файловая система

- Данные физически распределены по множеству серверов
- Для пользователя и приложений выглядит как **единое хранилище**
- Основные цели:
  - Масштабируемость до экзабайт
  - Высокая отказоустойчивость
  - Высокая пропускная способность (throughput)

**Два основных класса**:
- **File-oriented DFS** — HDFS, CephFS, Lustre
- **Object Storage** — MinIO, S3, Ceph RGW

---

## Основные виды распределённых хранилищ (2026)

1. **Классические DFS** — HDFS-подобные (master-slave)
2. **Параллельные FS** — Lustre, BeeGFS (HPC)
3. **Унифицированные** — Ceph (file + block + object)
4. **Объектные** — MinIO, SeaweedFS (S3-совместимые)
5. **Гибридные** — JuiceFS, HDFS + S3

**Тренд 2026**:  
HDFS доминирует в существующих on-prem кластерах, новые проекты — на MinIO / Ceph

---

## HDFS — текущее состояние (апрель 2026)

- **Версия**: Apache Hadoop 3.5.0
- По-прежнему активно используется для **Data Lake**
- MapReduce почти вытеснен, но **HDFS остаётся основой**
- Ключевые улучшения:
  - Erasure Coding
  - NameNode HA + Observer
  - Federation
  - Cloud connectors

**HDFS — зрелое, надёжное решение** для больших batch-нагрузок

---

## Архитектура HDFS

![bg right:45% width:400px](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/images/hdfsarchitecture.png)

**Основной принцип**:
- Данные делятся на **блоки** (128 или 256 МБ)
- Клиент получает **метаданные** от NameNode
- Реальные данные читает/пишет **напрямую** у DataNode

---

## Компоненты HDFS кластера (High Availability)

- **Active NameNode** — главный мастер, хранит метаданные (namespace, расположение блоков)
- **Standby NameNode** — горячий резерв
- **JournalNodes** (3–5 шт.) — хранят журнал изменений (edits log)
- **ZooKeeper** — координация и выборы Active/Standby
- **DataNode** — рабочие узлы (сотни/тысячи), хранят блоки
- **Client** — Spark, Hive, приложения

**Heartbeat + Block Reports** — DataNode регулярно отчитывается NameNode

---

## Архитектурные особенности HDFS

- **Write-once, Read-many** (WORM)
- **Data Locality** — вычисления рядом с данными
- **Rack Awareness** — реплики на разных стойках
- **Erasure Coding** — экономия до 50% места вместо 3x-репликации
- **Self-healing** — автоматическое восстановление

**Ограничения**:
- Плохо работает с мелкими файлами
- Не полностью POSIX-совместим

---

## Характеристики HDFS

| Требование                    | HDFS                              | 
|-------------------------------|-----------------------------------|
| Масштабируемость              | Тысячи узлов, десятки ПБ          |
| Отказоустойчивость            | Репликация + EC + HA              |
| Throughput (sequential)       | >200 МБ/с                         | 
| High Availability             | NameNode HA + JournalNodes        | 
| Low Latency / Random I/O      | Слабая                            | 
| Стоимость                     | Commodity hardware                |

## Ceph — унифицированное хранилище

![bg right:40% width:400px](https://docs.ceph.com/en/reef/_images/ditaa-e01d23327b5f34ba68b18dbe5923c7617eeab3a2.pngg)

- **CRUSH-алгоритм** — полностью распределённый, без центрального мастера
- **Unified Storage**:
  - CephFS — файлы
  - RBD — блочные устройства
  - RGW — S3 объекты
- горизонтально масштабируемость до экзабайт

---

Основные компоненты:


  * **OSD** — хранение данных
  * **MON** — контроль состояния кластера
  * **MDS** — метаданные для CephFS
  * **CRUSH** — placement algorithm для распределения объектов

---

```
         Client
            │
       ┌───────────┐
       │   MDS     │ (метаданные CephFS)
       └────┬──────┘
            │
          ┌─┴─┐
          │OSD│ (объекты)
          └─┬─┘
            |
            │
      Физические диски
```

* Каждый файл = блоки -> объекты RADOS
* CRUSH вычисляет, на каких OSD хранить объект
* Поддержка репликации или erasure coding

## GlusterFS

![bg right:40%](https://i.imgur.com/9kLmPqR.png)

- **Brick** — базовая единица хранения
- Полностью распределённая архитектура
- Очень простое масштабирование
- Идеально для: backup, media, home-директорий

---

В GlusterFS нет центрального сервера для метаданных. Файлы просто лежат на “bricks” — это обычные папки на обычных дисках разных серверов.

- Каждый brick = директория на сервере
- Несколько bricks вместе образуют volume
- Клиент видит volume как один большой сетевой диск

---

- Каждый новый файл кладётся на любой свободный brick
- Файлы распределяются равномерно между узлами
- Файл хранится на нескольких bricks одновременно
- Большой файл разбивается на куски
- Ускоряет чтение и запись больших файлов

---

- GlusterFS использует metadata in-line, хранит в каждом brick метаданные о том, какие куски файла здесь лежат
- Клиент может сверять checksum и lease (для реплик)
- Если brick недоступен, то GlusterFS идёт к другой реплике

---

## MinIO — объектное хранилище

* Лёгкое S3-совместимое объектное хранилище
* Простое горизонтальное масштабирование
* Основные компоненты:

  * MinIO Server — хранение объектов на локальных дисках
  * Клиенты используют S3 API

---

### Архитектура MinIO

* Distributed mode = несколько узлов + erasure coding
* Простое recovery и replication
* Нет блочного слоя и POSIX-файловой системы

---

### Особенности MinIO

* Минимальная конфигурация: один бинарник, можно контейнеризовать
* Идеально для Kubernetes и CI/CD
* Только объектное хранилище
* S3-совместимость = широкая поддержка приложений

---

## Сравнение систем (2026)

| Система     | Архитектура                  | Лучше всего для               | Масштаб      | Сложность     |
|-------------|------------------------------|-------------------------------|--------------|---------------|
| **HDFS**    | Master-Slave + HA            | Big Data, batch               | Петабайты    | Средняя       |
| **Ceph**    | CRUSH распределённая         | Unified (file+block+obj)      | Экзабайт     | Высокая       |
| **GlusterFS**| Brick-based                 | Простые file workloads        | Петабайты    | Низкая        |
| **MinIO**   | Object S3                    | Cloud-native, AI/ML           | Экзабайт     | Низкая        |

## Заключение и тенденции 2026+

**Главные тренды**:
- Объектные хранилища + Iceberg / Delta Lake
- Kubernetes + S3-совместимые системы
- Гибридные on-prem + cloud архитектуры

- Есть Hadoop-кластер ->  **HDFS**
- Новый проект -> **MinIO** или **Ceph**
